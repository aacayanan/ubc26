Closes #18.

Turns a round's stored verdicts into an outcome and a payout, exactly once. Before this, every piece of settlement existed but nothing called it: `resolveRoundOutcome` and `settleRoundStakes` had no production caller, a judged round sat in `EVALUATING` forever, and `score_events` / `user_scores` were never written.

## What changed

**Migrations**

- `20261119000800_f18_stakes_and_votes.sql` — `predictions.stake_points` (there was no stake amount, so the pot could not be computed); `place_stake()`, the single write path (join gate, deadline, over-balance, one stake per round, balance row locked); `score_events.kind` + unique key `(round_id, user_id, kind)` so a staker who also wins fan-favorite has two auditable events; 1000-point starter grant; `round_votes` + `cast_vote()` (minimal F32 — settlement needs a tally).
- `20261119000900_f18_settle_round.sql` — `settle_round()`, one transaction: settle every stake → write score events → credit balances with the streak rule → `competition_results` + `round_outcomes` → `transition_round`. The idempotency latch is the first check (a final round returns `alreadySettled` without writing). Also closes an F15 gap: `score_events` was guarded against UPDATE/DELETE after finalize, but not INSERT.
- `20261119001000_reconcile_funded_trigger.sql` — `supabase db diff --linked` showed the hosted project was missing `sync_funded` / `wallets_sync_funded`. F18 made `users.funded` load-bearing (`place_stake` gates on it), so this recreates the trigger and re-derives the column.

**Ledger model:** points are **not escrowed** at stake time. `user_scores.total_points` is the settled balance; an open stake reserves against it arithmetically. A loss or a void therefore needs no refund — `points_awarded = 0` is the whole story, and `score_events.points >= 0` stays true.

**Services** (`lib/server/services/scoring/`)

- `parimutuel.ts` — pure pot math. Largest-remainder split so credited points equal the pot **exactly**; deterministic tie-break by prediction id; void and unbacked-winner paths; fan-favorite awards (25 pts per voter of the crowd's winner).
- `settlement.ts` — reuses F15's `classifyModelOutcome` / `resolveRoundOutcome` rather than restating the rules; writes nothing when a round is `incomplete` / `retryable`; one `settle_round` call for every effect.
- `stakes.ts`, `votes.ts` — typed RPC wrappers with SQLSTATE → HTTP mapping.
- `stake-history.ts` — the signed-in account's stake history.

**Routes:** `POST /api/rounds/[id]/stakes`, `POST /api/rounds/[id]/votes`, `POST /api/internal/jobs/settle-rounds`, `GET /api/stakes`, `GET /api/rounds/[id]`.

**UI:** the round page, the predictions page and `/dev/pipeline/[id]` were all hardcoded stubs (`const round = null`, `const stakes = []`, and a route that did not exist) — every link in the demo loop was a dead end. All three now load real data.

**Tooling:** `scripts/db-test.mjs` + `scripts/db-local/bootstrap.sql` run the `supabase/tests/*.sql` suite against a throwaway Postgres container (Supabase-shaped roles, `auth` schema, `auth.uid()`, default grants). `scripts/settle-round.mjs` settles a round. `dev-pipeline-run.mjs` gains `--open` / `--lock`.

## Acceptance criteria

| Criterion | Status |
|---|---|
| Settlement is transactional/idempotent, cannot double-pay | ✅ one `settle_round` transaction + latch; verified live — a second call returned `already-final` with 0 credits |
| Ties, forfeits, void follow documented rules | ✅ F15 resolver reused; live run: Gemini forfeited on a `drawFrame` error (never judged), DeepSeek sole conformer → sole-conformer path |
| Stakes and payouts auditable per user and per round | ✅ `predictions` (stake / outcome / awarded) + `score_events` (kind) + `user_scores`; `/predictions` shows it |
| No stake after the deadline influences the pool | ✅ `place_stake` checks status and deadline under the database clock; asserted in SQL |

## Verification

- `npm run db:test` — all 7 SQL suites pass; both F18 migrations re-apply cleanly (idempotent, `--twice`).
- `npm test` — 266 passing. `typecheck`, `lint`, `prettier` clean.
- Live on the hosted project: staked 250 pts through the UI → locked → pipeline → settled. The round reached `SETTLED`, winner DeepSeek, 1 stake settled. Re-firing returned `already-final`.

## Not included (follow-ups)

- **F19 results view** — `/results` is still a stub, so a settled outcome is visible only in `/predictions` and the dev watch page.
- **F32 voting UI** — the vote API exists but has no interface, so `fan_favorite_model_id` is always null and the fan-favorite award has never fired.
- **Live per-model odds (F9/F27)** — only the round-level pot is surfaced. Odds moving *after* renders exist would break the two-clocks rule; live odds belong to the OPEN window only.
- Leaderboard hit rate stays pending; streaks are defined here (`F18_STREAKS_FINAL = true`).
- `PRODUCT.md` says practice accounts may vote while F32's text says funded-only; implemented as any signed-in account, flagged for reconciliation.
- On-chain stake commitments (F20) — `commitment_hash` is recorded but nothing verifies it.

## Notes for review

- **`predictions` now has two writer classes.** `place_stake` is the RPC a client may call; the column grants still allow a direct `insert` by `authenticated` with no amount or balance check. Tightening that (revoking direct insert) is a follow-up — it should land with F20's commitment path so nothing legitimate depends on the old grant.
- **Testing convention.** `f18_settlement.sql` simulates the caller with `set_config('request.jwt.claim.sub', …)` rather than `set role`, because the RPCs are `security definer` keyed on `auth.uid()`. Existing suites use statement-level `set local role`, which is still how `rls.sql` works.
- `rls.sql` needed three fixture fixes, all pre-existing breakage from the F8 signup trigger: profile and score rows now exist before the test inserts them (upsert instead of insert), and the challenges assertion now counts its own fixture rows instead of a global total.
